    Standard Library

    What comes with Lakescript. Its modules are under std/ and are imported with use *(i.e. use std/fs;, see the module path in modules.md)*. out, outln, err, errln, exit and the built-in exceptions can be used without use.

    Philosophy

    • If people keep writing the same helper in their scripts, the standard library is missing something. Common operations get a function or a method, even the simple ones *(i.e. $text.capitalize(), $list.unique(), $path.removeSuffix('.log'))*. A script should read as what it does, not as the helpers it needed first.
    • Methods, not procedural functions. Operations on a value are methods on that value: $list.length(), not len($list), and $list.push($item), not array_push($list, $item). Global functions are only for things that don't belong to a value *(i.e. outln, exit)*.
    • Primitive types first. If a built-in type is enough, it's used, so day-to-day scripts don't need to learn extra types. Paths are strings, the files of a folder are a list<string>, an exit code is a number *(like Python's os.listdir() and os.path.join())*.
    • A new type only when the built-in ones aren't enough, never a map pretending to be one. A map with fixed keys used as an object *(i.e. {'size' => 10, 'modified' => ...} for a file) means a real type is missing. Older modules use separate functions instead (i.e. fs::size(), fs::modified()), from before the standard library could declare classes. Maps are only for data whose keys aren't known in advance (i.e. env::all(), JSON)*.
    • Types as specific as possible. Signatures use generics instead of any *(i.e. sortBy<K>((T) -> K $key))*. any is only for values whose type really can't be known (i.e. JSON read without a schema) or functions that accept every value *(i.e. outln)*.
    • Values, not class hierarchies. Classes of the standard library are values that functions give back *(i.e. the http::Response of http::get())*: scripts read their fields and call their methods, but never have to create them, extend them or implement interfaces to use a module.
    • Full names. length(), not len(). trimStart(), not lstrip(). Abbreviations are only used when they're the common name of the thing *(i.e. toJson(), max())*.

    Naming conventions

    • **Questions end with ?.** Methods that take no arguments and ask something about the value end with ? *(i.e. $list.empty?(), $n.even?(), $text.blank?()). Methods that take an argument read as a sentence and don't (i.e. $text.startsWith('a'), $list.contains(5))*.
    • Strings and ranges never change. Their methods always return a new value *(i.e. $name.upper() returns a new string, $name is the same)*.
    • Lists and maps: verbs change, past participles copy. $list.sort() sorts the list itself, $list.sorted() returns a sorted copy and leaves the list as it was. The same goes for reverse/reversed, shuffle/shuffled and merge/merged. Methods that build something new from the values *(i.e. map, filter, unique)* always return a new list or map.
    • **Missing things are null, broken things throw.** Searching for something that isn't there returns null *(i.e. 'abc'.indexOf('z'), [].first()). Asking for something invalid throws (i.e. 'abc'.toNumber(), $list.removeAt(10))*.
    • Errors are the built-in exceptions *(ValueError, IndexError, ... see errors.md)*.

    How modules are made

    A module is written in Rust, in Lakescript, or both:

    • Rust, in crates/lakescript/src/stdlib/, for what needs the system or speed *(i.e. std/fs). Their signatures come from the tables in these notes (see tools/docs/prelude.py)*.
    • Lakescript, in a .lks file embedded in the interpreter, for classes and for what's easier to write in the language itself *(i.e. std/http, stdlib/http.lks)*. They're checked like any other module, so their types and the /// comments of their declarations reach the checker and editors.
    • Both: the Lakescript part uses its Rust part as std/<name>/native *(i.e. use std/http/native;)*. Only modules of the standard library can use the native modules, and they aren't documented, since scripts never see them.

    Errors in an embedded module name it as <std>/http.lks.

    • Rust data in a value: a native part can give the Lakescript part data of its own, like a parsed page, as a value scripts never see *(a Value::Handle)*. It's kept in a field of a class that isn't pub, and freed when nothing uses it anymore *(i.e. html::Element, see html.md)*. Printing an object leaves those fields out.
    • Functions that run Lakescript code: most native functions only get their arguments, but some get the VM, to run code they're given or make *(a Function::Vm, i.e. template::render, test::throws)*.

    Files

    **Templates end in .elks**, for "embedded Lakescript", like Ruby's .erb: page.html.elks is a template that gives HTML, notes.md.elks one that gives Markdown. So editors know which files have {{ }} tags with Lakescript inside: farsub highlights them as HTML with Lakescript in its tags. renderFile takes any file, with this extension or not.

    Tags

    • **{{ expression }} writes its value**, as outln writes it. null writes nothing, so {{ $user['nickname'] }} leaves nothing on the page when there's no nickname.
    • Blocks: for, if, else if, else and while open a block without {, with what's inside written as in Lakescript *(i.e. {{ for ($item in $items) }}, {{ if ($n > 1) }})*. Each block closes with its own end: {{ endfor }}, {{ endif }}, {{ endwhile }}. So nested blocks don't end in a row of {{ } }} like PHP's <?php } ?>, and an end in the wrong place says which block it expected.
    • What changes a variable writes nothing: const and let *(i.e. {{ const $total = $prices.sum() }}), assignments (i.e. {{ $i += 1 }})*, break and continue. {{ // ... }} is a comment, and ends at the first }}.
    • **An if that gives a value** is an expression, not a block: {{ if ($n > 1) 'items' else 'item' }} writes one of them. A tag is a block when the condition in parentheses is all there is after the if.
    • A line with only a block tag, a definition or a comment disappears, also its new line, so a template of a config file or of Markdown doesn't fill up with empty lines.
    • **A {{ in the text** is written as {{ '{{' }}.

    What a template sees

    • The keys of the map, as constants *(i.e. 'title' is $title)*. A key that isn't a valid name throws a ValueError.
    • The built-in functions and the methods of the values.
    • Not the variables of the script that renders it, nor its modules. A function is passed in the map *(i.e. {'money' => ($n) -> f"{$n} €"}, then {{ $money($price) }})*.

    HTML

    • With HTML escaping on, <, >, &, " and ' in the values that are written become entities, so a value a user typed can't add HTML to the page. The text of the template itself is never changed.
    • {{ raw($x) }} writes a value without escaping it.

    Errors

    A template becomes Lakescript code that builds the string, and runs as a script of its own whose variables are the values given. Its errors point at the line and column of the template, also the ones of the language *(i.e. page.html.elks:12:9: error: $nmae isn't declared)*, and $e.line() is that line. A template made with render is <template> in its errors.

    • A name that isn't declared is found when its tag runs, not before, since the values only come with the call.
    • A block that isn't closed, an end of another block *(i.e. {{ endif }} closing a {{ for }})*, an {{ else }} outside an {{ if }} and a {{ without }} are errors before anything runs.
    • A template can't catch errors: a try is a block, which tags don't have. The script that renders it can.

    How it's made

    The template is turned into the code of a script: its text is written by __text(n), {{ $x }} becomes __write($x), {{ raw($x) }} becomes __raw($x), and a block becomes the block of the language with { and }. render and renderFile are functions that run Lakescript code, so they get the VM *(a Function::Vm)*, while the other functions of the standard library only get their arguments. Where each part of the code came from is kept, to move errors back to the template.

    • Nothing is cached: every call turns the template into code and compiles it again. A small template takes about 13 µs per render in a release build, against about 0.6 µs for the same string built by hand, which scripts don't notice. A cache is left out until a script needs it.
    • A template is code: it can do anything a script can. Templates are written by the author of the script, so a template that came from a user must never be rendered, as with ERB and Jinja.

    Backlog

    • Templates that include others *(i.e. {{ include('header.html') }})*.
    • use inside templates.
    • A cache of compiled templates, by their text and the names of their values, if rendering the same template many times gets slow.
